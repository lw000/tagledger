# 06 技术架构文档

> 描述 tagledger / TagLedger（工业点表（tag ledger）管理 HTTP 服务，原名 collector，2026-11-15 人工确认更名）的整体系统结构、核心模块职责、依赖与交互关系、技术选型及理由、数据流向与部署形态。术语与 `CODEBUDDY.md` 通用术语表及本文件附录 B 一致；文中条款引用：C/P/S/B/F 系列见 `CODEBUDDY.md`（通用 AI 开发规范）；"硬性约束 N"指本文件附录 A 的项目硬性约束条目。

## 1. 系统概述与部署形态

单进程 C++17 HTTP 服务，无外部服务依赖（无数据库、无消息队列），CSV 文件为唯一持久化载体；配套原生 Web 前端单页。**部署形态为绿色目录部署**：

```
<deploy_dir>/                     一台主机可多实例：每实例独立端口 + 独立 data 目录
├─ tagledger(.exe)                唯一可执行文件（静态链接业务与第三方库）
├─ web/index.html                 前端单页（构建后由 CMake 拷贝到位）
├─ config/whitelist.conf          白名单配置（缺失则进入"开放模式"并 WARN）
└─ data/*.csv                     点表数据（运行期生成，可直接用 Excel 打开）
```

启动参数：`--port / --data-dir / --web-dir / --config-dir`（路径注入符合 S6，服务层不硬编码路径）。跨平台：同一源码树在 Windows（MinGW/MSVC）与 Linux（gcc，链接 pthread）下构建（硬性约束 1/2）。

## 4. 模块间依赖与交互关系

**依赖图（单向，无环，符合 F4）：**

```
apps/tagledger/main.cpp ──► services/http_server ──► services/csv_store ──► common/util
        │                          │        ▲              │        ▲            ▲
        │                          │        │              │        │            │
        │                          │        └── 内部白名单 ─┘        │            │
        │                          │               （HttpServer 组合持有）         │
        ├──► common/app_config（toml 解析）──┤                                  │
        ├──► common/shutdown ◄── http_server(admin 端点) ──────────────────────┘
        └──► common/util

依赖方向（F4 单向）：apps → services → common → third_party；服务间仅经公开头显式接口（S4）。
```

**关键交互序列：**

1. **写请求**：client → 白名单（放行）→ api 校验（文件名/枚举/JSON 包络）→ PointStore `unique_lock` → 内存修改 → `<file>.csv.tmp` → `rename_replace` 原子替换 → 统一包络响应。任一校验失败即整批拒绝，不落盘（硬性约束 5）。
2. **读请求**：client → 白名单 → api → PointStore `shared_lock` → 磁盘加载解析（无缓存，外部改文件即时生效）→ 分页/单行 → 统一包络。
3. **白名单拒绝**：pre_routing 阶段 403/40301 短路（不进路由），服务端 WARN 审计日志记录来源 IP/Origin（C7）。
4. **优雅退出**：SIGINT/SIGTERM/SIGBREAK → 信号处理器（仅写原子标志）→ monitor 线程 → 幂等 request_stop；或 `POST /api/admin/shutdown`（白名单保护）→ 请求线程 request_stop → main：`HttpServer::stop()`（幂等：停接新连接 → 排空在途请求 → join 监听线程）→ 存储析构 → 收尾日志（硬性约束 10）。

## 6. 数据流向

**写路径（保证一致性）：**
```
JSON 请求 → 字段校验(name/枚举/长度) → 文件名过滤(防目录穿越)
  → unique_lock(file) → 内存修改(重名/越界校验)
  → 全量写出 <file>.csv.tmp → rename_replace 原子替换 → 释放锁
```
并发保证：per-file `shared_mutex`；读读并行、读写/写写互斥；20 并发追加实证无丢失（docs/04 第 6 节）。批量写为单锁整批事务（术语：批量事务）。

**读路径**：`shared_lock` → 磁盘全量解析 → 内存分页 → 统一包络。无缓存层，一致性强、实现简单，10 万行规模毫秒级延迟满足需求（取舍见 docs/02）。

**退出路径数据安全**：在途写已在"线程池 join 排空"前完成；即使进程被强杀，原子替换保证 data 目录只有旧完整文件或新完整文件，无 `.tmp` 残留（集成测试实证）。

## 8. 已知架构限制

1. 全量读写模型：数据量超出单文件 10 万行量级时需引入分片或索引（当前需求不涉及）。
2. 白名单启动时加载，运行期修改需重启（可演进为管理端点热加载）。
3. 单进程单实例绑定一组端口/数据目录，无内建主备；多实例靠"多端口+隔离 data 目录"横向隔离。
4. 服务层尚未接入"服务管理器+公共基类"框架（CODEBUDDY.md B 系列与六要素为单服务阶段的预留演进路径，当前组件数不满足提炼门槛）。

## 附录 A：项目硬性约束与项目速查（自 CODEBUDDY.md 迁入，项目专属）

> 本附录承载项目专属裁决性条款；通用规范见根目录 `CODEBUDDY.md`（P5：冲突时以本附录为准）。

**工具链注意**：2026-11-15 本机工具链由 MinGW GCC 8.1.0 升级为 **GCC 16.2.0（C:\mingw64，gdb 17.2）**，CMake 升级为 **4.5.0**。旧工具链的 `std::filesystem` 编译期缺陷（`bits/fs_path.h:237` 的 `path` 比较运算符无法解析）与 `libstdc++fs.a` 缺失问题已消除（最小程序 `-std=c++17` 直接编译链接运行实测通过，无需额外链接库）。`std::filesystem` **禁令解除**；经人工确认按方案 A 完成迁移：`util.h` 文件操作层（`path_join/file_exists/rename_replace/list_csv_files/make_dirs`）内部实现已改用 `std::filesystem`（`std::error_code` 重载，不抛异常），公开 API 与行为不变，全仓平台分支（`_findfirst`/`GetFileAttributesA`/`_mkdir`/`opendir`）已消除。

**C++17 工具链适配登记（C1）**：GCC 16 起标准头不再透传提供 `<cstdint>`。历史登记：cxxopts 2.2.0 自身未包含该头，曾要求 `apps/tagledger/main.cpp` 前置 `#include <cstdint>`（F2 顺序的唯一已登记例外）。**该例外已于 2026-11-21 作废**：cxxopts 经人工裁决登记升级至 3.3.1（`CXXOPTS__VERSION_*` 实测 3/3/1），3.3.1 自身包含 `#include <cstdint>`（其头文件第 30 行），`main.cpp` 前置适配已移除，构建实测通过。

1. **C++17**：可使用 `std::optional`、`std::shared_mutex`、结构化绑定、`std::filesystem` 等；原 `std::filesystem` 禁令随工具链升级解除（见上），文件操作统一入口仍为 `util.h` 封装（内部为 std::filesystem 适配）。
2. **依赖封闭**：参与构建的白名单库为项目根目录 `third_party/` 下七个库（cpp-httplib、nlohmann、rapidcsv、catch2、cxxopts、toml++、spdlog）。不得把白名单外任何库接入构建，不得引入数据库。`third_party/` 下**所有文件严禁修改**（唯一例外：各库的 `README.md`，允许更新以登记说明；白名单库升级经 F5/Q6 流程登记后整体替换，如 2026-11-21 cxxopts 2.2.0→3.3.1）。**备用库区**（2026-11-21 人工裁决入库）：目录内另有 29 项源码库条目随仓库分发、仅供检索备料，未接入构建、不在白名单内；启用任一条目必须先走 F5/Q6 流程登记白名单并经人工确认，启用前禁止任何 include/CMake 引用。nlohmann 版本为 3.12.0（2026-11-15 由 3.1.2 升级，原"无 `contains()`"适配条款作废，存量 `find() != end()` 用法保持兼容；2026-11-21 工作区同版本覆盖差异经人工裁决回退至登记副本）；spdlog 版本为 1.17.0（编译库形态 `spdlog_lib`，日志统一入口为 `common/logger`，配置见 app.toml `[log]` 段）。
3. **接口规范冻结**：API 前缀 `/api/v1`，统一包络 `{"code":<0或业务码>,"message":...,"data"|"details":...}`；业务码 = HTTP 状态码×100+序号（40001/40002/40301/40401/40402/40501/40901/50001）。新增/修改接口必须同步更新 `docs/02-方案设计.md` 与冒烟脚本。
4. **CSV 规范**：字段固定 6 列 `name,io_address,address_type,point_type,rw,desc`；UTF-8 带 BOM；枚举值 `address_type∈{memory,io,constant}`、`point_type∈{bool,int,uint,float,double,string}`、`rw∈{rw,ro,wo}`；文件名仅 `[A-Za-z0-9_-]{1,64}`（服务端必须拒绝其他字符，防目录穿越）。
5. **写路径安全**：所有写操作必须走 `PointStore` 的锁（`shared_mutex` per file）+ 临时文件原子替换；禁止绕过锁直接读写 CSV 文件。
6. **白名单**：所有路由（含静态页面与健康检查）必须经过 `set_pre_routing_handler` 中的白名单；未命中返回 403/40301 并记 WARN 日志；不得解析 `X-Forwarded-For`。
7. **前端禁令**：`web/` 只能用原生 HTML/CSS/JS（fetch、DOM），禁止任何第三方库/CDN/构建工具。
8. **error_handler 语义**：httplib 0.66 对所有 `status>=400` 回调 error_handler；业务 handler 已写错误体时（`res.body` 非空）必须跳过，不得覆盖。
9. **测试规范**（详见 docs/05）：单元测试与性能压测只用 Catch2 v3.16（`<catch2/...>` 包含根为 third_party；`catch_user_config.hpp` 是构建期生成物，勿手工创建）；用例命名 `<模块>/<行为>` + 标签 `[unit]/[perf]/[shutdown]`+模块；`TEST_CASE` 中 `a == b && c` 必须整体加括号；测试目标禁止自写 main。集成脚本用 **Python 标准库**，输出 ASCII，退出码即结果。
10. **安全退出**：信号处理器内只写 `sig_atomic_t` 与原子标志（其余动作在 monitor 线程）；信号安装在组件构造后、监听前；资源释放顺序固定：`svr.stop()` → `listen_thread.join()`（httplib 排空任务队列）→ 存储析构 → 日志 flush。修改退出逻辑必须同步 `docs/05-测试与安全退出规范.md` 第 5.4 节的验证要点表。
11. **文档同步**：行为变化必须同步 `docs/02-方案设计.md`（接口/存储规范）、`docs/05-测试与安全退出规范.md`（测试/退出规范）与 `docs/04-测试验证报告.md`（验证结论）。
12. **模块化规范**：新增子服务、公共基类或调整目录结构时，必须逐条满足 CODEBUDDY.md《模块化子服务规范》S/B/F 系列；触发条件（第二个子服务出现）成立时先重组目录再写代码。
13. **参数解析与配置解析强制**（人工确认的方案 A，2026-11-15；cxxopts 版本 2026-11-21 经人工裁决升级为 v3.3.1）：命令行参数解析**强制使用 cxxopts**（`third_party/cxxopts`，v3.3.1）；程序配置文件解析**强制使用 toml++**（`third_party/toml`，v3.4.0）；不得替换为其他同类库，不得自研等价实现。配置文件为 `config/app.toml`，优先级：命令行 > app.toml > 内置默认（键表见 docs/02 第 9 节；`config_dir` 有引导依赖，不可经 app.toml 设置）。

**接口与退出关键约定**：
- **读**：`GET /api/v1/points?file&index`（单读）、`GET /api/v1/points?file&start&count`（批量读，count=0 到文件尾）；**写**：`POST /api/v1/points`（带 index 为修改，不带为追加）、`POST /api/v1/points/batch`（整批事务）；**文件**：`GET/POST /api/v1/files`；**退出**：`POST /api/admin/shutdown`（白名单保护，幂等触发优雅退出）。
- 错误码表与请求/响应结构以 `docs/02-方案设计.md` 第 3、4 节为准，代码中的 `StoreError` 枚举值必须与业务码一致。
- 安全退出顺序固定：`svr.stop()` → `listen_thread.join()` → 存储析构 → 日志 flush（详见 docs/05 第 5.3 节）。

## 附录 B：项目专属术语补充

| 术语 | 定义 |
| --- | --- |
| 统一包络 | 所有接口响应共用的一致 JSON 结构：code / message / data 或 details |
| 业务码 | 错误标识 = HTTP 状态码×100 + 序号（如 40901），置于统一包络的 code 字段 |
| 白名单中间件 | 在路由分发前按来源 IP/Origin 过滤请求的拦截层，未命中返回 403 并记审计日志 |
| 开放模式 | 白名单配置缺失时放行所有来源的降级模式，启动时必须以 WARN 显式提示 |
| 批量事务 | 整批写操作单锁内先全量校验、全部合法才落盘的原子性保证 |
